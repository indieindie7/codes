# Performance engineering of real-time shallow-water / height-field simulation for games

Scope: GPU vs CPU-SIMD implementations, memory layout, sparse/tiled grids with sleeping, adaptive resolution, time-step strategies, threading, and known pitfalls. Context given by the coordinator (treated as given, not independently sourced): Hydrophobia (2011) ran explicit HLL SWE on 20-unit cells, SSE 4-wide, sheets of up to ~1200 cells per room, CFL 0.5 sub-stepping, midpoint time stepping, worker threads, double-buffered grids, mesh built on other jobs. Targets: (a) a modern-GPU game context, (b) a CPU-side 2D blood-pool sim in a Direct3D-9-era mod, 32x32 to 128x128 cells, many pools.

Method note: most primary PDFs (Müller GDC 2008 slides, Chentanez & Müller 2010, Brodtkorb et al. 2012 x2, Kurganov & Petrova 2007, Horváth et al. 2016, Tavakkol & Lynett 2017, Sætra et al. AMR 2015, Kallin 2008) were downloaded and text-extracted locally; quotes/numbers below come from those extracted texts unless marked otherwise. Several paywalled pages (ScienceDirect, MDPI, Springer) returned 403 and are reported only via search snippets, flagged as such.

## KQ1. GPU implementations of SWE / height-field water: patterns, throughput, per-frame cost

### Takeaway
Two GPU lineages exist: (1) the graphics "ping-pong render target" lineage (NVIDIA DX9 WaterInteraction 2004, Celeris in HLSL, sdthompson's KP07 HLSL demo) that stores h/velocity/flux in texels and runs 1-3 full-screen passes per step, and (2) the CUDA stencil lineage (SINTEF/Brodtkorb-Sætra, Horváth "Kepler shuffle", Chentanez-Müller) that tiles the domain into 16x12 or 16x16 thread blocks with apron/ghost cells in shared memory. Measured throughput for a 2nd-order Kurganov-Petrova scheme is ~530 Mcells/s on one GTX 480 (2012), >1.2 Gcells/s on 4 Fermi GPUs, with a 128x128 game-quality SWE step costing ~0.75 ms on a GTX 480 in Chentanez-Müller's examples; a 256x256 step cost ~1.28 ms.

### Cited Findings
- Brodtkorb, Sætra & Altinakar 2012 (Computers & Fluids 55): single-GPU KP07 implementation with "a performance of 530 megacells per second" (abstract); GTX 480, single precision; block size 16x12 = 192 threads chosen as multiple of warp size 32; shared memory width padded to 33 to avoid bank conflicts; "using three blocks, corresponding to 18 warps, yielded the best performance" per SM; L1 cache preferred over texture cache on Fermi. — [Brodtkorb et al. 2012, PDF](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf)
- Same paper: packing of flux + source terms into "three values for R ... reduces the memory footprint by approximately 31%"; the flux kernel loads interior + "two neighbouring cells in each direction" into shared memory; a "single warp" does the extra apron flux computations to avoid duplicate work; the time-integration kernel uses 32x16 = 512 threads since it is not shared-memory-limited. — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf)
- Same paper, Figure 10: full-domain performance plotted up to ~400 Mcells/s (1st-order Euler) and lower for 2nd-order RK2; counting only wet cells, the curve reaches ~1600 Mcells/s for domains of 5-35 Mcells (axis labels read from extracted figure text). — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf)
- Multi-GPU: "domains consisting of up to 235 million cells at a rate of over 1.2 gigacells per second using four Fermi-generation GPUs", row decomposition with ghost-cell exchange. — [SINTEF publication page](https://www.sintef.no/en/publications/publication/?pubid=CRIStin+888971); [Sætra & Brodtkorb, Shallow Water Simulations on Multiple GPUs](https://link.springer.com/chapter/10.1007/978-3-642-28145-7_6)
- Ghost-cell expansion lets multiple steps run between exchanges: "for an overlap of six cells, we would be able to run three time steps before having to exchange"; "an overlap of on the order of tens of cells yields highest performance". The same idea applies to tiles on one device. — [Brodtkorb & Sætra, CMWR 2012 guidelines](https://brodtkorb.org/files/publications/brodtkorb_saetra_cmwr_2012.pdf)
- Horváth et al. 2016 ("Kepler shuffle"): flux kernel 16x16 threads per block; 32 registers/thread; using warp shuffle instead of shared memory cut per-block shared memory from "16 x 17 x 18 x 4 = 19,584 bytes" (occupancy 25%) to "16 x 17 x 4 x 4 = 4352 bytes" (near 100% occupancy); shared-memory arrays padded to blocksize+1 to avoid bank conflicts in the y direction; "Blocks should contain at least 192 threads to hide" latency. Benchmarks on a GeForce Titan, CUDA 6.5, Malpasset grid 1149x612 cells of 15 m. — [Horváth et al. 2016, PDF](http://drivenbynostalgia.com/files/keplershuffle/paper.pdf)
- Chentanez & Müller 2010 (CUDA, GTX 480, Core i7 2.67 GHz): height-field step "HF" (advection, height integration, velocity integration, PML, overshoot reduction, FFT texcoord advection) = 0.75 ms for 128x128 (WaterF, Beach), 1.28 ms for 256x256 (Ocean), 2.19 ms for a 900x135 grid (Boat); whole frame incl. rendering 7.97-18.05 ms on GPU. The same boat scene on the CPU with 1-4 threads: HF 42.25 / 25.69 / 23.25 / 19.06 ms (i.e. the GPU is ~9-19x faster than the multi-threaded CPU path for a 121k-cell grid). — [Chentanez & Müller 2010, PDF](https://matthias-research.github.io/pages/publications/hfFluid.pdf)
- DX9-era ping-pong pattern (NVIDIA WaterInteraction, 2004): state in "a single A8R8G8B8 texture ... Height is kept in the blue and alpha colors, velocity in the green, and force in the red"; "two texture render targets used in a ping-pong fashion"; on ps1.1 the update is 2 passes (3 neighbours, then 4th neighbour + integrate) plus "A third pass smoothes neighboring positions and velocities in order to reduce undesirable high frequency oscillations". Also couples a tiling simulation texture with a movable "local detail" texture that follows the character. — [NVIDIA Water Interaction tech report](https://download.nvidia.com/developer/SDK/Individual_Samples/DEMOS/Direct3D9/src/WaterInteraction/docs/WaterInteraction.pdf)
- Celeris (Tavakkol & Lynett 2017): Boussinesq/NLSW hybrid FV-FD on a uniform Cartesian grid in C++ + HLSL via Direct3D; "the problem must be reformulated in terms of graphics primitives and the data must be stored within textures"; each step passes state/bathymetry/gradient textures to a shader whose output is a render target; sample config uses 601x601 cells, dt = 0.005 s, epsilon = 5e-12 (their desingularization epsilon); the dispersive terms give "a tridiagonal system of equations for each row/column". Speed anecdote: a 234x201-cell test that took 3.3 h on a Pentium 4 completes "in less than 15 s, on a PC with NVIDIA Quadro K600" (an entry-level GPU). — [Celeris arXiv 1611.05984](https://arxiv.org/pdf/1611.05984)
- Celeris is built on Stephen Thompson's open Direct3D/HLSL KP07 demo ("kp07.hlsl" simulation shader + "shallow_water.fx" rendering), GPL-3. — [sdthompson1/shallow-water-demo](https://github.com/sdthompson1/shallow-water-demo)
- Celeris explicitly says the scheme "supports a dry state with no need to keep track of the wet-dry front" (KP07 property). — [Celeris](https://arxiv.org/pdf/1611.05984)
- Hagen, Hjelmervik, Lie, Natvig & Henriksen 2005, "Visual simulation of shallow-water waves" (Simulation Modelling Practice and Theory 13(8):716-726) is the earliest GPU SWE paper cited by the SINTEF group. — cited in [CMWR 2012](https://brodtkorb.org/files/publications/brodtkorb_saetra_cmwr_2012.pdf)
- gpu-ocean (metno) is a CUDA/PyCUDA framework for rotational SWE (ensembles, data assimilation); the old repo is archived (Nov 2023) and redirects to metno/gpuocean; GPL-3. No throughput numbers in the README. — [metno/gpu-ocean](https://github.com/metno/gpu-ocean); [metno/gpuocean](https://github.com/metno/gpuocean)
- Brodtkorb's warning on speedup claims: theoretical CPU/GPU gap "currently lies at around 7 times"; "speedup claims of hundreds or more require a thorough explanation"; report % of peak via profiling instead. — [CMWR 2012](https://brodtkorb.org/files/publications/brodtkorb_saetra_cmwr_2012.pdf)
- Recent flood-model literature reports "over 40 times more efficient than the CPU code" for GPU tsunami tests and ~710x over serial for multi-GPU (search snippets; not primary-verified). — [search result, multi-GPU SWE arXiv 2010.14416](https://arxiv.org/pdf/2010.14416)

### Inferences
- Per-frame cost scaling (inferred from the 530 Mcells/s KP07/RK2 figure on a 2010 GPU): 256^2 = 65k cells -> ~0.12 ms per RK2 step; 512^2 -> ~0.5 ms; 1024^2 -> ~2 ms. Launch overhead and small-grid under-occupancy will dominate at 256^2 (the 2012 curves only approach peak above several million cells), so expect ~0.3-1 ms floors per step for small grids on 2010-era hardware; modern GPUs with 5-10x the bandwidth should land at 0.1-0.5 ms for 512^2. With 2-4 CFL sub-steps per frame, a 1024^2 SWE sheet is still only a few ms on a modern GPU. Flag: inference from the cited throughput, not a measured game number.
- The Chentanez-Müller 0.75 ms at 128^2 (which includes PML, overshoot reduction and FFT advection, i.e. ~6 kernel launches) suggests launch/sync overhead, not arithmetic, dominates small grids; batching many small pools into one texture atlas / one dispatch is the natural fix.
- For a D3D9 engine, the Celeris/sdthompson path proves a full KP07 solver fits in SM3 pixel shaders with MRT render targets; the NVIDIA 2004 sample proves even the ps1.1 wave equation works. But readback to the CPU (for gameplay queries such as "is this cell bloody") is the expensive part on D3D9 (GetRenderTargetData stalls); that is the usual reason to keep small gameplay-relevant pools on the CPU.

### Gaps
- No source gives measured cells/s for exactly 256^2 / 512^2 / 1024^2 on current (2024-26) GPUs; numbers above are 2010-2016 hardware. The Horváth 2016 gigacells/s figure (Fig. 13) could not be read from the extracted text.
- gpu-ocean's performance numbers were not retrievable (README only).

## KQ2. CPU SIMD: lane layout, branchless wet/dry, cache blocking, fusing sub-steps, measured numbers

### Takeaway
Open SWE codes that vectorise on CPU all use structure-of-arrays (separate h, hu, hv planes), inner-loop vectorisation across the x index, and report 20-30x gains from vectorised flux computation + cache blocking (hms++). The branchless-mask wet/dry pattern Hydrophobia used is the same one GPU codes use implicitly (SIMT masks); KP07's desingularisation formula is itself branch-free. No source gives absolute AVX2 cells/s for a small game grid; the only CPU timing found is Chentanez-Müller's 19-42 ms for a 121k-cell SWE step on a 2010 Core i7 (not SIMD-tuned).

### Cited Findings
- hms++ (TU Berlin, open-source SWE): "using a cache-blocking structure for the time marching loop, and vectorisation of flux computations, leads to a speedup of around 30x"; "vectorisation of flux computations ... speedups of up to 27x over the baseline"; uses Eigen for explicit SIMD, OpenMP within a node, MPI across nodes. (Search snippets; full paper 403.) — [hms++ SoftwareX](https://www.sciencedirect.com/science/article/pii/S2352711023000936); [hms++ project page](https://www.tu.berlin/en/wahyd/research/research-projects/model-development-and-hydroinformatics/hms-fast-extensible-and-user-friendly-shallow-water-equations-solver)
- TUM SWE teaching code (f-wave / HLLE Riemann solvers, OpenMP/MPI/CUDA backends): vectorisation is done via "#pragma omp simd" with reductions and "#pragma omp declare simd" on Riemann-solver functions; with -O3 "iterations over patches are automatically vectorized using AVX-512" (search snippets referencing TUM theses and the UPC++ actor paper). — [TUM-I5/SWE](https://github.com/TUM-I5/SWE); [UPC++ actor library paper, TUM](https://mediatum.ub.tum.de/doc/1520197/1520197.pdf)
- Brodtkorb's CPU baseline for a 2D stencil is the plain SoA form `h_new[j*nx+i] = 0.25*(h[n]+h[s]+h[e]+h[w]) - 0.5*dt/dx*(hu[e]-hu[w]) - 0.5*dt/dy*(hv[n]-hv[s])` over separate h, hu, hv arrays; he notes CPU caches do automatically what GPU shared-memory aprons do by hand. — [CMWR 2012](https://brodtkorb.org/files/publications/brodtkorb_saetra_cmwr_2012.pdf)
- CPU vs GPU peak: "Intel Core i7-3960X can have up-to 6 cores x 8-way SIMD = 48 floating point units, whilst ... GeForce 580 GTX ... 16 cores x 32-way SIMD = 512" (2012). — [CMWR 2012](https://brodtkorb.org/files/publications/brodtkorb_saetra_cmwr_2012.pdf)
- Chentanez & Müller 2010 CPU path (multi-threaded, not described as SIMD): HF step on a 900x135 grid 42.25 ms (1 thread) to 19.06 ms (4 threads), i.e. ~2.2x on 4 threads. — [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf)
- KP07 desingularisation `u = sqrt(2) h (hu) / sqrt(h^4 + max(h^4, eps))` is a pure arithmetic expression; the authors then set `(hu) := h * u` so fluxes stay consistent — both are branch-free and SIMD-friendly. — [Kurganov & Petrova 2007, eqs. 2.17, 2.21, 3.24-3.25](https://people.tamu.edu/~gpetrova//KPSV.pdf)
- Brodtkorb's wet/dry threshold is also branch-free: "setting water depths less than eps_m to zero, where eps_m is close to machine precision" (a max/select). — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf)
- Chentanez & Müller's "face is reflective if h_i,j <= eps and H_i,j > eta_i+1,j (or symmetric)", eps = 1e-4 dx, is a per-face predicate that in SIMD becomes a mask zeroing the face velocity. — [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf)
- xsimd provides portable C++ wrappers for SSE/AVX/AVX-512/NEON with the same select/mask idioms. — [xtensor-stack/xsimd](https://github.com/xtensor-stack/xsimd)
- Kass & Miller 1990 (via Bridson's lecture notes) is the implicit CPU alternative: ADI split so "Each implicit solve only uses one part of A, logically a tridiagonal matrix: can solve really" fast; "But, can cause weird grid artifacts if dt too big". — [Bridson CS533B slides on Kass-Miller](https://www.cs.ubc.ca/~rbridson/courses/533b-winter-2004/cs533b_slides_mar11.pdf); [Kass & Miller 1990](https://ohiostate.pressbooks.pub/app/uploads/sites/45/2017/09/kass-miller.pdf)

### Inferences
- Lane layout for a 32-128 wide pool grid: rows padded to a multiple of 8 (AVX2) or 16 (AVX-512) plus a 1-2 cell halo on each side so the i-1/i+1 neighbours are unaligned loads from the same row, and j+-1 are the adjacent rows; SoA planes h, hu, hv (and B, terrain) each padded identically. A 128x128 sheet is 3 planes x 64 KB = 192 KB in float — fits L2 on any modern core, so cache blocking only matters for sheets > ~512^2; for Hydrophobia-size sheets (~1200 cells) the whole state sits in L1.
- Fusing CFL sub-steps: an explicit stencil step cannot be fused across sub-steps without ghost-cell expansion (the same trick Brodtkorb uses between GPUs — compute k extra halo cells per row-block to run k steps without re-syncing). On a single core this buys little; it matters only when the sheet is split across worker threads (fewer barriers). Inference from the ghost-cell-expansion finding.
- Expected throughput: a KP07/HLL flux is ~100-200 flops per face; at 8 lanes x ~2 FMA/cycle x 3-4 GHz a single AVX2 core should process on the order of 50-150 Mcells/s for a first-order step, so a 128x128 pool (16k cells) at 2-4 sub-steps per frame costs on the order of 0.3-1 ms per core, and 32x32 pools cost ~20-60 us each. Flag: back-of-envelope, not measured; hms++'s 27-30x vectorisation+blocking speedup over naive scalar C++ supports the magnitude.
- Hydrophobia's SSE 4-wide select-by-mask code maps 1:1 to AVX2 `_mm256_blendv_ps` / AVX-512 `k`-mask ops; widening to 8 lanes mostly requires the row padding change above.

### Gaps
- No open code with published AVX2/AVX-512 cells/s for small (<=128^2) SWE grids was found; hms++ and SERGHEI report relative speedups only, and the hms++ full text was paywalled.
- The Hydrophobia implementation details are from the coordinator's context, not from a public source.

## KQ3. Sparse / tiled grids, sleeping, wake-on-stamp, wet bounding boxes

### Takeaway
Every serious SWE implementation skips dry work at block granularity: Brodtkorb's "early exit" (compute a per-block wet flag in the integration kernel, skip flux work if the block and its 4 neighbours are dry) and Sætra's "sparse compute / sparse memory" (compact a list of wet block indices and launch only those). The same flag also catches lake-at-rest (R = 0) blocks — i.e. "sleeping" of still water. Müller's GDC advice is simply "Simulate active and visible regions only (sleeping)" with sparse tiling of irregular domains.

### Cited Findings
- Early exit: "if a block does not contain water at all, we can simply skip all computations for that block ... In the time integration kernel, we let each block perform shared memory reduction to find out if this block contains any water at all, and write to an auxiliary buffer ... In the flux kernel we then read from this buffer, and if the block and its four closest neighbouring blocks are dry, we can skip flux calculations all together." "The presence of one single wet cell in a block is sufficient to consider the whole block as wet." — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf)
- Sleeping still water: "We have also developed this technique to mark cells where the source terms perfectly balance the fluxes (R = 0) as 'dry'. This extends the early exit strategy to also optimize for wet blocks where the steady state property holds." — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf)
- Adaptive fallback: the early-exit kernel has a small cost (extra reads/writes + reductions); "Once the kernel execution time for the early exit kernel exceeds the execution time for the regular kernel, we swap over to using the regular kernel" and re-probe "every hundredth timestep". — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf)
- Sparse compute (Sætra): "At the end of each time step, each block stores -1 in a buffer if it is dry and no water may flow into it in the next time step, or its grid position otherwise. At the next time-step, this buffer is sorted so that the non-negative indices come first, and a grid with of one block per non-negative index is launched." Sparse memory goes further: "wet blocks are stored after one another in GPU global memory", at the cost of complicated apron reads. Figure 3 compares Full / Early Exit / Sparse Memory / Sparse Compute on a dry-bed dam break with ~26% wet cells — all sparse variants beat full-domain by a large factor (the figure is normalised; exact ratios not readable from text). — [CMWR 2012](https://brodtkorb.org/files/publications/brodtkorb_saetra_cmwr_2012.pdf); [Sætra, Shallow Water Simulation on GPUs for Sparse Domains (ENUMATH 2011)](https://link.springer.com/chapter/10.1007/978-3-642-33134-3_71)
- Wake-neighbours rule (Horváth 2016): "Initially, all blocks are marked as wet. After evolving ... whether there is at least one wet cell in the block ... If a block is active, its neighbors could be flooded in the next time step, thus, all adjacent blocks are activated, too. Indices of active blocks are compacted and used by the flux and time integration kernels"; blocks with hydrograph (source) cells are force-activated; the integration kernel marks blocks active that "contain wet cells or have cells with nonzero discharges". — [Horváth et al. 2016](http://drivenbynostalgia.com/files/keplershuffle/paper.pdf)
- Why the dry-skip is safe: "the compact stencil ensures that water will travel at most one cell per time step". — [CMWR 2012](https://brodtkorb.org/files/publications/brodtkorb_saetra_cmwr_2012.pdf)
- Müller GDC 2008 / GDC 2007: "Simulate active and visible regions only (sleeping)", "Level of detail (LOD)"; irregular domains via "Sparse tiling" of height-field patches, with the z-buffer resolving terrain intersections. — [Müller GDC 2008 slides](https://media.gdcvault.com/gdc08/slides/S6509i1.pdf); [Müller, Real Time Fluids in Games 2007](https://www.cs.ubc.ca/~rbridson/fluidsimulation/GameFluids2007.pdf)
- Kallin 2008 (quadtree height-field for games): "Benchmarking shows that there is no practical performance hit of having inactive (dry) areas in the grid making it feasible to let the grid cover the entire virtual environment"; dry cells could be deactivated/dynamically freed. — [Kallin, Real Time Large Scale Fluids for Games](https://ep.liu.se/ecp/034/010/ecp083410.pdf)
- Chentanez & Müller 2010 grid-shifting: "The simulation grid is shifted in whole multiple of grid spacing dx to be approximately centered around" the object of interest (a moving window rather than a world-size grid). — [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf)
- NVIDIA's 2004 DX9 sample does the same with textures: a tiling far-field simulation plus a "local detail" simulation texture whose borders match the tiled one and which is "free to move around to follow the character". — [NVIDIA Water Interaction](https://download.nvidia.com/developer/SDK/Individual_Samples/DEMOS/Direct3D9/src/WaterInteraction/docs/WaterInteraction.pdf)

### Inferences
- A CPU blood-pool version of this: tile each pool sheet in 8x8 (one AVX row = 8 lanes) or 16x16 tiles with two bitmasks per tile: `wet` (any h > eps) and `active` (any |hu|,|hv| or |dh/dt| above a sleep threshold, or R != 0). Step only tiles that are active or adjacent to an active tile; a stamp (footprint, drip, body) sets `active` on the tile it hits and its 8 neighbours. The wake-neighbours rule is the exact Horváth/Brodtkorb rule, and the one-cell-per-step CFL argument guarantees nothing is missed. Hydrophobia's wet bounding box is the degenerate 1-tile-list version of this; a tile list handles many disjoint pools better than one box.
- Sleep threshold: Brodtkorb's R = 0 test is exact only for lake-at-rest with balanced source terms; in a game use `max|velocity| < v_sleep` and `max|dh| < h_sleep` for N consecutive steps, then freeze the tile (and optionally snap velocities to zero so it is exactly still). A viscous liquid (blood) with friction/damping reaches that threshold quickly, which is the main reason sleeping pays off for pools.
- The early-exit "probe and fall back" trick carries over to CPU: if more than ~70-80% of tiles are active, skip the tile bookkeeping and step the whole sheet.

### Gaps
- Exact speedup ratios of early-exit vs sparse-compute vs sparse-memory (CMWR Fig. 3) are not extractable from the PDF text; the ENUMATH 2011 Sætra chapter is paywalled.
- No public game-engine source document (beyond the Müller slides) describes a tile sleeping policy with thresholds; thresholds above are inference.

## KQ4. Adaptive resolution / LOD (quadtree SWE, nested grids, multiple sheets)

### Takeaway
Block-based (tile) AMR with nested child grids is the proven structure both on GPU (Sætra-Brodtkorb-Lie 2015) and for games (Kallin 2008 quadtree); the hard parts are conservation at coarse/fine interfaces (flux correction), ghost-cell space-time interpolation, and stability at resolution jumps — Kallin reports explicit schemes that were stable on uniform grids blew up at coarse/fine boundaries. For games the simpler route is several independent sheets at different resolutions (Müller's "Physics low-res, appearance hi-res") or a moving high-res window inside a coarse/tiled far field (NVIDIA 2004, Chentanez-Müller grid shifting).

### Cited Findings
- Sætra, Brodtkorb & Lie 2015, GPU AMR for KP07: "a block-based strategy will group cells together and refine" — refinement decided per tile via a 32x4-thread shared-memory reduction counting cells meeting the criterion, so "a certain fraction of the cells must fulfill the refinement criteria before a tile is refined"; "padding of new refined areas is necessary and this comes automatically when using tiles" (waves need room to propagate before reaching a new patch boundary). — [Sætra et al. 2015, PDF](https://brodtkorb.org/files/publications/saetra_brodtkorb_lie_amr.pdf)
- Time stepping across levels: "No grid on refinement level l can be integrated in time before all grids on levels k = 0..l-1 are at least one time step ahead"; parent provides ghost values by "space-time interpolation ... for all the intermediate time steps on all level l+1 grids"; "the last time step must often be reduced to reach t exactly"; "estimates of maximum eigenvalues ... increase with increasing resolution, causing allowed step sizes to decrease with increasing refinement level". — [Sætra et al. 2015](https://brodtkorb.org/files/publications/saetra_brodtkorb_lie_amr.pdf)
- Conservation: a "Flux correction" kernel (kernel 8) "maintains conservation of mass" by accumulating interface fluxes weighted by dt on both sides and correcting the coarse cell with the (assumed more accurate) fine-side sum; a "Downsample" kernel (7) replaces parent cells by child averages. Also "no interface between a parent and a child grid, or two child grids at the same refinement level, crosses each other". — [Sætra et al. 2015](https://brodtkorb.org/files/publications/saetra_brodtkorb_lie_amr.pdf)
- Kallin 2008 (quadtree height field for games): explicit Euler with upwind differencing on a quadtree; cells are forced "to never deal with neighbors that are smaller than themselves" (use the parent of the smaller neighbour); smoothing-kernel interpolation whose bandwidth depends on cell size; "explicit methods with parameters that give stable simulations on an uniform grid can produce instabilities in heterogeneous grids in the boundaries between high and low resolution. This hints at a demand for implicit methods"; "central differences resulted in high frequency noise and undampened oscillations" so upwind was used. — [Kallin 2008](https://ep.liu.se/ecp/034/010/ecp083410.pdf)
- Dazzi, Vacondio, Dal Palù & Mignosa 2018: local time stepping on "block-uniform Quadtree grids featuring locally the same time step" on GPU, "speed-ups of 2.8 without degrading the solution accuracy" on top of the GPU speedup (search snippets; full text paywalled). — [Dazzi et al. 2018, Adv. Water Resources 111](https://www.sciencedirect.com/science/article/abs/pii/S0309170817304311)
- Müller: "Reduction dimension 3d -> 2d; Physics low-res, appearance hi-res (shader effects); Simulate active and visible regions only (sleeping); Level of detail (LOD)". — [Müller GDC 2008](https://media.gdcvault.com/gdc08/slides/S6509i1.pdf)
- Chentanez & Müller 2010 add sub-grid detail without refining the solver: a high-resolution wave texture advected by the SWE velocity (3 sets of texture coordinates reset every tau seconds with phase shift tau/3) is used "for bump mapping in all examples" and to displace "a high resolution rendering grid with a grid spacing of 1/4 dx" in the boat example. — [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf)

### Inferences
- For a modern game: a 2-level nested scheme (coarse world sheet 2-4 m cells, one or two fine 0.25-0.5 m windows around the player/boat, Dirichlet ghost cells interpolated from the coarse grid each sub-step, flux-correct the coarse cells under the fine window every coarse step) captures most of the AMR benefit with none of the regridding machinery. The Sætra padding rule says: make the fine window larger than the region of interest by a few cells per expected step before re-centering.
- For the blood-pool mod: independent fixed-resolution sheets per pool (32^2 for small splats, 128^2 for a flooded floor) are the right LOD; no coupling needed because pools are disjoint. Pick cell size per pool from the body footprint (Hydrophobia's 20-unit cells vs ~1200-cell rooms implies they also fixed resolution per room).

### Gaps
- Dazzi 2018 and the MDPI LTS paper (Water 14(6):922) were paywalled/blocked, so the LTS synchronisation and flux-correction details come only from abstracts and the AMR paper.

## KQ5. Time stepping: CFL sub-stepping vs implicit, local time stepping, bounded sub-step counts, semi-Lagrangian advection, dissipation, damping for viscous liquids

### Takeaway
Explicit FV schemes (KP07/HLL) need dt <= CFL * dx / max(|u| + sqrt(g h)), with CFL 1/4 (Brodtkorb, Horváth) to 1/2 (KP07 positivity proof) in 2D; positivity of h is only guaranteed under that limit. Games bound cost by (a) clamping velocity/wave speed so a fixed number of sub-steps is always enough (Chentanez-Müller: |u| <= alpha dx/dt, alpha = 0.5, plus a depth cap for the height update) or (b) using an unconditionally stable implicit (Kass-Miller ADI tridiagonal) or semi-Lagrangian advection, which trade accuracy for stability and add damping. Scheme-induced dissipation is countered cheaply with MacCormack/BFECC-style correction or 2nd-order (minmod) reconstruction; deliberate damping for blood/mud is done multiplicatively per step with a dt-normalised factor.

### Cited Findings
- CFL in 2D for KP07 on GPU: "dt <= 1/4 min{ dx / max|u +- sqrt(gh)|, dy / max|v +- sqrt(gh)| }" (eq. 8), i.e. disturbances travel "at most one quarter grid cell per time step"; the max is found by a per-block shared-memory reduction, then a single-block global reduction, "dt = 0.25 r". Horváth: "We use CFL = 0.25 in all our simulations". — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf); [Horváth et al. 2016](http://drivenbynostalgia.com/files/keplershuffle/paper.pdf)
- KP07's positivity proof requires "the CFL restriction lambda a <= 1/2" (1D, a = max local speed) under forward Euler, and extends to any SSP-RK since those are "a convex combination of several forward Euler steps". — [Kurganov & Petrova 2007](https://people.tamu.edu/~gpetrova//KPSV.pdf)
- Brodtkorb: using first-order Euler instead of RK2 "gives minimal changes in the" Malpasset results; Figure 10 shows Euler (A, B) faster than RK2 (C, D). — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf)
- Müller's wave-equation form: "Information can only propagate 1 cell per time step ... c < h/dt or dt < h/c (CFL)"; "Explicit Euler ... Assumes velocity constant during a time step" -> overshoot; and the 2007 slides describe the integrator as "semi-implicit Euler" (update v then u with new v). — [Müller GDC 2008](https://media.gdcvault.com/gdc08/slides/S6509i1.pdf); [Müller 2007](https://www.cs.ubc.ca/~rbridson/fluidsimulation/GameFluids2007.pdf)
- Müller's three damping options: "Damping force (physically 'correct') f = -k v, But how to choose k? No stability guarantees"; "Scaling (unphysical, more direct control) v = s v // s < 1, smaller time step -> stronger effect"; "Clamping ... offset = avg(4 neighbours) - u[i,j]; maxOffset = maxSlope * h // independence of resolution h; if (offset > maxOffset) u[i,j] += offset - maxOffset" (and symmetric). Hello-world uses `v *= 0.99` per step. — [Müller GDC 2008](https://media.gdcvault.com/gdc08/slides/S6509i1.pdf)
- Chentanez & Müller bounded-cost stabilisers: "clamp the magnitudes of u and v to be less than alpha dx/dt, where we use alpha = 0.5"; "limit the water depth used for the height integration by replacing h-bar by h-bar - h_adj, where h_adj = max(0, avg of 4 neighbours' h-bar - h_avgmax) and h_avgmax = beta dx / (g dt), beta = 2.0" — "This places a limit on the wave lengths and amplitudes in deep water regions, but improves the stability"; fixed dt = 16.66 ms (20 ms for boat) in all examples; "our stability enhancements cannot guarantee unconditional stability. However, they allow us to explicitly integrate with a reasonable time step". — [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf)
- Chentanez & Müller advection: velocity self-advection uses the "conditionally stable modified MacCormack method as in [SFK08] and fall back to the semi-Lagrangian method if the" result is out of the local min/max; time splitting: advect velocity first, then integrate height and velocity. Overshooting at shallow fronts ("wave lengths become smaller than dx ... become numerical ripples ... explicit integration ... amplify the edge of the first wave") is treated by a dedicated overshooting-reduction step that does not conserve volume. — [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf); [Selle, Fedkiw et al., An Unconditionally Stable MacCormack Method](https://physbam.stanford.edu/papers/stanford2006-09.pdf)
- Semi-Lagrangian dissipation and remedies: semi-Lagrangian advection is "unconditionally stable" but "numerical dissipation increases fluid viscosity"; BFECC "advects the solution forward and then backward in time" and costs 3 semi-Lagrangian passes; the modified MacCormack needs 2 (search summary of Huang et al. and Selle et al.). — [Huang et al., Reducing numerical dissipation](https://users.cs.utah.edu/~ladislav/huang15reducing/huang15reducing.pdf); [Selle et al. 2006](https://faculty.cc.gatech.edu/~jarek/papers/maccormack.pdf)
- Kass & Miller 1990: linearised SWE -> wave equation with c^2 = g d, solved by "an alternating-direction implicit method ... solving a simple tridiagonal linear system for each row and column"; "A single iteration per frame suffices in most cases"; it handles "net transport of water and boundary conditions with changing topology" (wetting/drying). Bridson's notes: "Caveat: to handle H going to 0 or negative" special care is needed, and ADI "can cause weird grid artifacts if dt too big". — [Kass & Miller 1990](https://ohiostate.pressbooks.pub/app/uploads/sites/45/2017/09/kass-miller.pdf); [Bridson notes](https://www.cs.ubc.ca/~rbridson/courses/533b-winter-2004/cs533b_slides_mar11.pdf)
- Celeris uses 3rd-order Adams-Bashforth predictor + optional 4th-order Adams-Moulton corrector with a fixed user dt (0.005 s on a 601^2 grid; 0.001 s on 2000x65), and Euler for the first two steps; the implicit dispersive part is a per-row/column tridiagonal solve on the GPU. — [Celeris](https://arxiv.org/pdf/1611.05984)
- Friction as implicit/semi-implicit source: Brodtkorb added "semi-implicit physical friction terms" (Manning) for stability; Chentanez-Müller's PML damping uses "0 < gamma_decay < 1 and 0 < gamma_update < 1 ... to help improve the stability of the explicit Euler time integration", gamma_decay = 0.9, gamma_update = 0.1, 10-cell damping region, sigma increasing "quadratically or cubically" toward the border. — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf); [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf)
- Pipe-model (virtual pipes) practical damping, from lisyarus' game-dev write-up: `flow = flow * frictionFactor + (eta_left - eta_right) * g * dt / dx` with `frictionFactor = pow(1 - friction, dt)` so damping is "timestep-independent"; optional viscosity scales flows by `H^2 / (H^2 + 3 dt nu)`; working dt "around 0.001 to 0.01"; "Larger timesteps cause instability". Known limitation: the model "doesn't have inertia and velocity diffusion". — [lisyarus, Simulating water over terrain](https://lisyarus.github.io/blog/posts/simulating-water-over-terrain.html)
- Local time stepping: Dazzi et al. 2018 report 2.8x from LTS on GPU; Sætra 2015 implement per-level dt with sync at root steps (details in KQ4). — [Dazzi et al. 2018](https://www.sciencedirect.com/science/article/abs/pii/S0309170817304311); [Sætra et al. 2015](https://brodtkorb.org/files/publications/saetra_brodtkorb_lie_amr.pdf)
- Horváth 2016 notes a hidden time-step cost of spurious wet/dry velocities: KP07 "requires more time steps to simulate" because high velocities at wet/dry boundaries shrink the CFL dt; their HWP14 reconstruction "allows for longer time steps". — [Horváth et al. 2016](http://drivenbynostalgia.com/files/keplershuffle/paper.pdf)

### Inferences
- Bounded-cost recipe for a game (combining Chentanez-Müller clamps with Hydrophobia's CFL 0.5 sub-stepping): choose a fixed max sub-step count N per frame (e.g. 4 at 60 Hz => dt_sub ~ 4.2 ms), then clamp |u| and sqrt(g h) so that (|u| + sqrt(g h)) dt_sub / dx <= 0.5 always holds; the clamp is only reached in violent frames and acts as "velocity-limited" rather than "time-step-limited" cost. For blood on a floor, h is centimetres, so sqrt(g h) ~ 0.3-1 m/s; with 10-20 cm cells one sub-step per frame at 60 Hz already satisfies CFL 0.5 (dt_max ~ 0.05-0.1 s), so sub-stepping is rarely needed — the cost driver is the number of pools, not the sub-step count.
- Local time stepping in a game is best done per sheet/pool (each pool chooses its own N from its own max wave speed), not per tile within a sheet; the per-level synchronisation and flux correction of true LTS is not worth it for disjoint pools.
- Dissipation control cheaply: for a 1st-order HLL/Lax-Friedrichs-type scheme the cheapest counter is the minmod (theta ~ 1.3) MUSCL reconstruction KP07 already uses (2nd order in space) with Euler in time (Brodtkorb found RK2 made "minimal changes"); for the wave-equation/pipe model, Müller's `v *= s` with s = pow(s_per_second, dt) is the dt-normalised form (lisyarus' pow(1 - friction, dt)). For blood/mud, make the damping deliberately strong (large friction, viscosity term H^2/(H^2 + 3 dt nu)) — this also makes tiles reach the sleep threshold faster (KQ3).
- Implicit (Kass-Miller) is attractive for very viscous, slow blood where accuracy of wave speed is irrelevant: one tridiagonal sweep per row and column per frame is O(N) with tiny constants on 32-128 grids and is unconditionally stable for any dt; the known downsides are grid artefacts at large dt and extra care for H -> 0 (dry) cells. Inference: for a D3D9-era CPU mod this is probably the lowest-risk option if momentum/vortices are not needed.

### Gaps
- No source quantifies the damping (effective viscosity) introduced by HLL or Lax-Friedrichs on game-size grids in cells-per-wavelength terms; Hydrophobia's own tuning values are not public.
- The explicit-vs-implicit GPU comparison (MDPI Water 15(6):1165) was blocked (403).

## KQ6. Multi-threading / job systems and asynchronous (multi-rate) updates

### Takeaway
Published game/graphics sources describe the solver as a sequence of kernels on double-buffered state (read Q^n, write Q^{n+1}) with the rendering mesh/normal map generated from the finished buffer — exactly the Hydrophobia pattern. Explicit threading advice is thin: Chentanez-Müller's CPU path scaled only 2.2x on 4 threads; the GPU papers' tile-with-halo decomposition and ghost-cell expansion (run k steps per sync by widening the halo by k cells) are the transferable ideas for a CPU job system.

### Cited Findings
- Chentanez & Müller 2010: "For the CPU cases, the height field simulation and the particles simulation are multi threaded"; HF 42.25 ms (1 thread) -> 19.06 ms (4 threads) on a 900x135 grid. Solid coupling stayed on the CPU even in the GPU build ("Porting the solid coupling part to the GPU is part of future work") — coupling cost 2.2-3.1 ms per frame. — [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf)
- Kernel sequence on GPU (one explicit step): "1 boundary conditions, 2 flux [+ max dt], 3 max time step (reduction), 4 time integration" (Brodtkorb); Sætra 2015 lists Flux / Max time step / Time integration / Boundary conditions / Downsample / Flux correction, with two passes for RK2. — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf); [Sætra et al. 2015](https://brodtkorb.org/files/publications/saetra_brodtkorb_lie_amr.pdf)
- Ghost-cell expansion for fewer synchronisations: overlap of 6 cells => 3 steps without exchange; tens of cells optimal between GPUs; "An extension to this technique is to overlap data transfers with computation" (compute interior while halos exchange). — [CMWR 2012](https://brodtkorb.org/files/publications/brodtkorb_saetra_cmwr_2012.pdf)
- Non-determinism from parallel reductions: "floating point arithmetic is not commutative due to round off errors ... the sequence of floating point operations between different execution units often will be non-deterministic" — relevant to the max-wave-speed reduction that sets dt. — [CMWR 2012](https://brodtkorb.org/files/publications/brodtkorb_saetra_cmwr_2012.pdf)
- Rendering from the sim state is itself a shader pass in the GPU lineage: NVIDIA 2004 converts the height map to a normal/bump map in a pixel shader; Celeris passes "the flow state and terrain ... to the graphics renderer" after "a user-defined number of computational time steps" (multi-rate: several sim steps per rendered frame). — [NVIDIA Water Interaction](https://download.nvidia.com/developer/SDK/Individual_Samples/DEMOS/Direct3D9/src/WaterInteraction/docs/WaterInteraction.pdf); [Celeris](https://arxiv.org/pdf/1611.05984)
- Chentanez & Müller run the sim at the frame rate with fixed dt = 16.66 ms and a separate particle system; fast objects "may pass through many grid cells" in one step, so the coupling sub-steps the object path (their Algorithm 2 uses num_substeps along the sweep). — [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf)

### Inferences
- Job-system layout for many pools (CPU): one job per pool-sheet (or per 16-32 row band for sheets > ~256^2), each job owning its SoA planes and tile masks; a frame-level "stamp queue" collected from gameplay threads is applied at the start of the pool's job (so stamping never races the stepping loop — the double buffer means readers of the previous frame's h are safe at any time). Mesh/normal generation reads the completed front buffer as a separate job, as Hydrophobia did. Inferred from the double-buffer/kernel-sequence pattern above.
- Multi-rate: far or sleeping-adjacent pools step at 30 or 15 Hz with dt scaled accordingly (their CFL budget is usually slack because they are calm), near pools at 60 Hz; interpolate rendered heights between steps. This is the Celeris "several steps per render" pattern reversed. Inference.
- The dt-selection reduction should be avoided in a game (fixed sub-step dt + velocity clamp, KQ5) — that also removes the non-deterministic reduction Brodtkorb warns about.

### Gaps
- No public source describes a shipped game's SWE job graph in detail (the Hydrophobia description is from the coordinator); thread-scaling numbers beyond Chentanez-Müller's 4-thread CPU figures were not found.

## KQ7. Pitfalls: wet/dry oscillation, desingularisation, NaN guards, precision at large offsets, stamping thread-safety, determinism

### Takeaway
The documented failure modes are: (1) division hu/h at tiny h -> huge velocities -> tiny dt or blow-up (fix: KP07 desingularisation with eps tied to dx, plus snapping h < eps_m to 0); (2) negative depth from reconstruction/round-off (fix: KP07's wet/dry slope correction, or pipe-model outflow scaling); (3) spurious waves/velocities at wet/dry fronts (inherent to KP07's slope correction; HWP14 reconstruction fixes it); (4) storing water elevation w = h + B in float loses precision when B >> h (store h, or store values near zero); (5) parallel reductions and FMA/SSE/compiler differences break determinism (fix: fixed dt, same binary, /fp:strict, checksums).

### Cited Findings
- Desingularisation (KP07 eq. 2.17/3.24): `u = sqrt(2) h (hu) / sqrt(h^4 + max(h^4, eps))`, then recompute `(hu) := h * u` so fluxes use the corrected velocity; reduces to hu/h for large h; chosen over `u = h (hu) / sqrt(h^4 + eps)` because the correction factor is 1 (not 1/2) once h^4 >= eps, and because "division of small values of h (hu)" by tiny numbers was unreliable in experiments. KP used eps = max{dx^4, dy^4}. — [Kurganov & Petrova 2007](https://people.tamu.edu/~gpetrova//KPSV.pdf)
- Brodtkorb's practical eps: KP's dx^4 "is insufficient for many real-world applications" (dx = 15 m); they use `eps = K0 * max{1, min{dx, dy}}` with K0 = 1e-2 in single precision ("for a 15 meter grid cell size our approach desingularizes the fluxes for water depths less than 15 cm"); Malpasset actually needed eps = 40 cm; "Numerical round off errors may also make very small water depths negative ... setting water depths less than eps_m to zero, where eps_m is close to machine precision." Too large eps = large errors; too small = tiny time steps. — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf)
- Why: "we need to calculate u = hu/h. This calculation leads to large round-off errors as h approaches zero, which in turn can lead to very large velocities and even instabilities. Furthermore, as the timestep is directly proportional to the maximal velocity in the domain, this severely affects the propagation of the solution." — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf)
- Negative depth from 2nd-order reconstruction: "the use of a nonlinear limiter cannot guarantee positivity" of the point values; KP07 corrects the piecewise-linear w in cells where w_{j+-1/2} < B_{j+-1/2} by setting the low side to the bed height and the other to 2 w_j - B (eqs. 2.15-2.16); this is what makes the scheme positivity-preserving but "violates the well-balancedness of the scheme along the wet-dry interface, causing small initial waves emerging from these cells" (Brodtkorb). — [Kurganov & Petrova 2007](https://people.tamu.edu/~gpetrova//KPSV.pdf); [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf)
- Spurious wet/dry velocities and their cost: KP07 "suffers from incorrect high velocities along the wet/dry boundaries"; "velocity will grow smoothly in these formerly dry areas ... climbs up on the shores"; "if a cell becomes wet, it will almost never be completely dry again"; the HWP14 scheme (Horváth, Waser, Perdigão 2014) fixes this with a different reconstruction and a "draining time step technique (DTST)" so KP07 ends up "considerably slower" on real floods despite higher cells/s because it needs more steps. — [Horváth et al. 2016](http://drivenbynostalgia.com/files/keplershuffle/paper.pdf)
- Brodtkorb's parabolic-basin verification (Thacker): surface elevation matches, "For the velocities, however, we see that there is a growing error along the wet-dry" front. — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf)
- Chentanez-Müller's game-side wet/dry rules: h can go negative "Due to numerical error ... Therefore, we clamp h to always be >= 0"; a face is a wall unless the wet cell's surface is above the neighbouring dry cell's terrain ("the water level in a wet cell needs to be higher than the terrain level in the neighboring dry cell before the flow starts"), with eps = 1e-4 dx. — [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf)
- Pipe-model equivalent: scale all outgoing flows of a cell by `min(1, water * dx*dy/dt / total_outflow)` so a cell never goes negative; the author deliberately never forms velocity = flow/area because "zero divided by zero" at thin layers causes discontinuities. — [lisyarus](https://lisyarus.github.io/blog/posts/simulating-water-over-terrain.html)
- Hydrology thin-layer practice: a wet/dry threshold depth around 1e-3 m is common; "setting water level of dry nodes to the local bed level causes a spurious free surface slope"; "an extremely small threshold value can give rise to spurious surface slope, slow boundary movement, and boundary irregularities" (search summary of wetting-drying literature). — [A new method for the treatment of wetting-drying fronts](https://www.sciencedirect.com/science/article/pii/S0307904X11005269); [Wetting and drying for RKDG](https://www.oden.utexas.edu/media/reports/2008/0825.pdf)
- Precision: single precision is "sufficiently accurate" for KP07 because "errors in the measured bathymetry and errors caused by handling of the wet-dry interface will typically shadow the errors imposed by the use of single precision"; but "setting the water depth close to the machine precision will cause all fluxes to have very large errors". Storage pitfall: "it is often tempting to store the water elevation in memory. This, however, will give rise to large relative errors when the water depth is small compared to the elevation ... store the quantity of interest as a number close to zero in memory, and then reconstruct derived quantities on demand." — [Brodtkorb et al. 2012](https://brodtkorb.org/files/publications/brodtkorb_kp_on_gpus.pdf); [CMWR 2012](https://brodtkorb.org/files/publications/brodtkorb_saetra_cmwr_2012.pdf)
- Volume loss guard (Müller): "V = sum u[i,j]; Vnew = sum unew[i,j]; Distribute V - Vnew evenly, Within connected regions!" — a cheap global mass fix. Chentanez-Müller note their coupling and overshoot reduction "do not" conserve volume and point to a global adjustment [Hes07]. — [Müller GDC 2008](https://media.gdcvault.com/gdc08/slides/S6509i1.pdf); [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf)
- Stability clamps that double as NaN guards: velocity clamp |u| < alpha dx/dt (alpha 0.5) and the h_avgmax depth cap (KQ5). — [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf)
- Determinism: "SSE is 'too under-specified to be deterministic'" (Jon Watte, quoted); FMA and transcendental differences between CPUs; fixes: same compiler + same instruction set, `_controlfp(_PC_24, _MCW_PC)` + round-to-nearest re-asserted each tick, `/fp:strict`, avoid rsqrt/rcp approximations, per-frame state checksums (Pandemic's Battlezone 2 "magic sniper"); Gas Powered Games: "We have never had a problem with the IEEE standard across any PC cpu AMD and Intel with this approach". — [Gaffer on Games, Floating Point Determinism](https://gafferongames.com/post/floating_point_determinism/)
- Parallel-reduction order is non-deterministic across execution units (so a dt chosen by a parallel max is non-deterministic). — [CMWR 2012](https://brodtkorb.org/files/publications/brodtkorb_saetra_cmwr_2012.pdf)

### Inferences
- Blood-pool parameter set (inferred from the above): for dx = 0.1-0.25 m use KP07's eps formula: `eps = K0 * dx` with K0 ~ 1e-2 gives 1-2.5 mm, roughly the thickness of a visible smear; snap h < 1e-6 to 0 and zero its momentum. Store h (depth) not surface height; keep the pool's grid in local coordinates (origin at the pool) so world offsets never enter the float state. Clamp |u| to 0.5 dx/dt_sub each sub-step; after the step, `h = max(h, 0)`, and replace non-finite values by 0 (an `isfinite` select) as a last-resort guard — cheap in SIMD (`_mm256_cmp_ps` ordered compare). Flag: specific values are inference by analogy to Brodtkorb's 15 m -> 15 cm rule.
- The "a wet cell almost never becomes dry again" effect (Horváth) matters for pools that should visibly dry/soak: add an explicit drain/evaporation sink (h -= k dt) and let tiles sleep once h < eps everywhere.
- Thread-safety of stamping: because every cited scheme is double-buffered, the only hazard is writing stamps into the buffer currently being read as Q^n. Queue stamps and apply them at step start (or into Q^{n+1} after integration), never from another thread mid-step. Inference from the double-buffer/kernel structure.
- Deterministic networking: use a fixed sub-step dt (no max-speed reduction), fixed tile iteration order, and avoid approximate rsqrt in the sqrt(g h) wave-speed term; same-binary lockstep is then achievable per Gaffer's sources, but cross-platform (console vs PC, with/without FMA) is not without /fp:strict-equivalent on both sides.

### Gaps
- No public game post-mortem quantifies NaN-guard overhead or lists a shipped parameter set for blood/viscous SWE; values above are inferred.
- HWP14 (Horváth, Waser, Perdigão 2014) reconstruction details were only seen second-hand in the 2016 paper.
