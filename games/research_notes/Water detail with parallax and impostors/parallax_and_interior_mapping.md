# Parallax-family techniques for sub-cell water detail (POM / relief / interior mapping) on a D3D9 SM3 renderer

Scope: rendering only. The simulation (Hydrophobia-style 2D shallow-water height field, 20-unit cells) is taken as given and supplies, per cell, a height, a 2D velocity and (implicitly) a water depth above the floor. The question is whether ripples, a thin "sub-surface" layer with apparent depth, a floor seen through the water, and suspended detritus can be a parallax / interior-mapped *material* on the coarse surface mesh instead of finer geometry or a finer simulation.

Verification legend used below: **[P]** = read directly from the primary source (PDF text or page fetched); **[S]** = from a search-result snippet or secondary write-up only (not the primary document); **[I]** = my inference. Everything in "Cited Findings" is [P] unless marked otherwise.

## Key question 1 — POM / relief mapping on an animated height field, and ripples as a flow-advected normal/height layer (Vlachos 2010, Chentanez & Müller 2010): resolution, sample counts, cost on SM3

### Takeaway
The standard, shipped way to add sub-grid ripples to a simulated or artist-flowed water surface is *not* ray-marched parallax but a flow-advected **normal (or derivative/height) texture** blended in 2–3 phases: Valve did it on ps2.0b/Xbox 360 for +2 texture fetches and +21 ALU instructions over two scrolling normal maps; Chentanez & Müller advect three sets of texture coordinates per simulation cell through the velocity field (reset every ~3 s, phase-shifted) and look up an FFT wave texture for bump mapping (and optional displacement of a 4× finer render grid). Tatarchuk's POM (D3D9 SM3) explicitly supports dynamically rendered height fields with Sobel-derived normals and ran at 255 fps on a 2006 mid-range Radeon X1600 XL with 8–50 samples per pixel, so marching a ripple height field on 2011 hardware is affordable, but POM only shifts *texture lookups* — it adds apparent relief to the ripple pattern, it does not displace the water surface or its depth-buffer footprint.

### Cited Findings

**Valve, "Water Flow in Portal 2" (Vlachos, SIGGRAPH 2010 course) — flow-advected normal maps**
- Goals and constraints: "Solve repeating texture artifacts, Flow around obstacles, Vary water speed and bump strength"; technical: "Work with existing reflective surfaces; Min hardware ps2.0b (6-year-old hardware) & Xbox 360"; the water shader "had limited instructions left for our low end hardware ps2.0b". — [Vlachos 2010 PDF](https://www.advances.realtimerendering.com/s2010/Vlachos-Waterflow(SIGGRAPH%202010%20Advanced%20RealTime%20Rendering%20Course).pdf)
- Algorithm: "Pixel shader flow, not geometric flow"; keep a tiled ripple normal map; artists author a flow map (texture of 2D flow vectors) covering the whole surface at "Relatively low resolution: ~4 texels/meter", generated in Houdini (combed vector field + procedural masks) because it is "impractical to paint directly". — same source
- Builds on Max & Becker 1995 flow visualization: UV offset = flow vector × time; "Only distort a small amount... distortion looks reasonable for the first 1/3 of uv space"; so "Blend the short animated segment in two layers, each layer offset half a phase so we can hide the restart". — same source
- Two artifacts and fixes: "Repetition — the same normals will flow through the same point" → solved by offsetting the two layers; "Pulsing — the surface appears to pulse in a repeating pattern" → solved by a noise texture that de-synchronises the phase per pixel. — same source
- Bump strength tied to speed: "We scale down the strength of the normal in tangent space by the flow speed (Flow speed is the length of the 2D flow vector)". — same source
- Cost: "Compared to scrolling two normal maps: Additional texture fetches: 2 – flow & noise; Additional arithmetic pixel shader instructions: 21". — same source
- Portal 2 extension — flowing a *color* map for debris in dirty water: for normals the distortion interval runs from zero to some fraction with the peak at half distortion; for color/debris "offsetting the interval from −fraction to +fraction so the peak of the interval is at zero (the at-rest position)" works better, i.e. debris favours less distortion. — same source
- Future work listed by Valve (not shipped): "Flow height maps and use tessellation hardware; Multiple frequencies of normal maps; Render dynamic flow vectors per-frame so animated objects cause flow changes". — same source

**Catlike Coding "Texture Distortion" (flow-map tutorial, Unity) — the exact two-phase formulas**
- Decode `f = rg*2-1; f *= FlowStrength`; phases `o = 0` / `0.5`; `p = frac(t + o)` with `t = time*Speed + noise`; `uv = (uv - f*(p + FlowOffset))*Tiling + o + (t - p)*jump`; weight `w = 1 - |1 - 2p|` (triangle wave; `wA + wB = 1`); result `texA*wA + texB*wB`. Low-frequency Perlin noise stored in the flow map's A channel is added to time to spread the pulse. — [Catlike Coding](https://catlikecoding.com/unity/tutorials/flow/texture-distortion/)
- Jump per phase of roughly 0.2–0.25 (positive or negative) works well; a jump of 0.25 loops every 4 phases; mixed values (e.g. 6/25 and 5/24) give a theoretical loop of 600 phases. — same source
- Derivative-height ("DH") map trick: A = ∂h/∂x, G = ∂h/∂y (normal-map encoding), B = height; `dh = dh * w * heightScale`; `heightScale = speed * HeightScaleModulated + HeightScaleConstant`; combine phases by summing derivatives `d = dhA.xy + dhB.xy` then `n = normalize(float3(-d.x, -d.y, 1))` — summing derivatives is the correct way to combine height-based layers and avoids reconstructing Z per layer. Derivatives encode slopes up to 45° without extra scaling. — same source

**Chentanez & Müller 2010, "Real-time Simulation of Large Bodies of Water with Small Scale Details" (SCA 2010) — simulation-advected FFT ripple texture**
- Motivation: "The height field simulation... cannot resolve waves with wave lengths smaller than the grid resolution Δx"; decreasing Δx "would increase the number of cells and require a smaller time step". Requirements for the added small waves: advected with the velocity field; not distorted excessively; disappear if stretched too much; relatively cheap. — [Chentanez & Müller 2010 PDF](https://matthias-research.github.io/pages/publications/hfFluid.pdf) (Eurographics DL record: [diglib.eg.org](https://diglib.eg.org/items/d0320015-4b07-416b-8f41-047485c9f7f3))
- Method: an FFT wave simulation [Mastin et al. 1987, Tessendorf 1999] with periodic boundaries generates "a high resolution wave texture F(s,t)" containing "only high frequency waves"; texture coordinates and weights are computed at simulation grid points and bilinearly interpolated "for per-pixel bump mapping or for displacing the rendering grid. We use the texture for bump mapping in all examples. We also use it for displacing a high resolution rendering grid with a grid spacing of ¼Δx in the boat riding example." — same source
- Advection (Max & Becker [MB96] scheme): per grid cell store 3 sets of texture coordinates (s^k, t^k), k = 1..3, initialised to (iΔx, jΔx), transported by semi-Lagrangian advection, reset to (iΔx, jΔx) every τ seconds with a phase shift of τ/3 between sets; blend weights `w_k = (1/3)(1 − cos(2π (t − t0_k)/τ))` so the sum is constant; final displacement `ξ Σ_k w_k F(s_k, t_k)`; stretching weight `ξ = e^(−β μ)` where μ is the largest-magnitude eigenvalue of the Green strain of the texcoord map, β between 0.5 and 2; "We use τ ≈ 3 seconds in our examples"; τ "trades off the distortion of the texture coordinates against the coherency of the waves". Neyret's advected textures [Ney03] would avoid the tradeoff "but it is more expensive". — same source
- Figure 7 compares no FFT / constant-weight FFT (β = 0, "unnaturally distorted small waves") / varying-weight FFT (β = 1). — same source
- Also in the rendering section: choose the quad diagonal that aligns with wave crests (geometry shader) and make waves "choppy" by offsetting vertex (x,z) by c∇η clamped to Δx/2 to avoid self-intersection. — same source
- Hardware/timings: CUDA on NVIDIA GTX 480 + Core i7 2.67 GHz; grids 128×128 to 256×256 (boat 900×135); frame time (sim + render, ms): BeachG 9.88 total / HF 0.75; OceanG 13.13 / 1.28; WaterFG 7.97 / 0.75; the HF column "includes advection, height integration, velocity integration, PML, overshooting reduction and FFT texture coordinate advection". Δt = 16.66 ms. — same source
- Related: [BAB09] "Advected river textures" advects particles storing texture coordinates for small-scale detail (cited in the paper's related work). — same source

**Tatarchuk, "Practical Parallax Occlusion Mapping with Approximate Soft Shadows" (SIGGRAPH 2006 course ch. 5 / GDC 2006 / ShaderX5) — POM on D3D9 SM3**
- Pipeline: compute tangent-space view V_ts and light L_ts per vertex; compute parallax offset vector P (max texture-space offset) per vertex or pixel; in the pixel shader ray-cast V_ts along P sampling the height profile to find the intersection → shifted texcoord t_off; cast toward the light for a visibility coefficient; shade with maps sampled at t_off. — [Tatarchuk 2006 PDF](https://advances.realtimerendering.com/s2006/Chapter5-Parallax_Occlusion_Mapping_for_detailed_surface_rendering.pdf)
- Intersection: linear search with the height profile treated as **piecewise linear**, intersecting the ray with the segment between the first sample below the surface and the previous one — "combine the 8 bit precision due to bilinear texture filtering with the full 32 bit precision for root finding". Relief mapping's binary search "requires dependent texture fetches... latency cost which is not offset by any ALU computations"; its 8-bit filtered intersection gives "visible stair-stepping artifacts at steep viewing angles" and depth biasing "introduces excessive feature flattening at oblique angles". — same source
- Adaptive sample count (SM3 dynamic flow control): `n = n_min + (N·V_ts)(n_max − n_min)`; code: `int nNumSteps = (int) lerp(nMaxSamples, nMinSamples, dot(vViewWS, vNormalWS));` with early-out when a point below the surface is found; height map in the alpha of the normal map, sampled with `tex2Dgrad(..., dx, dy)` inside the loop. — same source (Listing 2)
- Step size vs texels: "At grazing angles, the parallax amount is quite large... the step size is frequently much larger than a texel, and thus unrelated to the texture resolution"; artists set the sample bounds per texture. Nyquist guidance: sample "at slightly more than twice the frequency of the height map features". — same source
- In-shader LOD: compute the mip level explicitly (`fMipLevel = max(0.5*log2(minTexCoordDelta), 0)`) and run plain bump mapping above a threshold (they used **threshold 4**), lerping POM→bump by the fractional mip; "Simply using mip-mapping for LOD management is ineffective since it does not reduce shader complexity". — same source
- Soft shadows: n samples along the light ray (figure shows n = 8), only computed where N·L ≥ 0 via dynamic branching. — same source
- Results: "DirectX 9.0c shader programs", SM 3.0 listings; textures 1024² RGB (non-contiguous), 256² and 128² repeated; 1,100-polygon soldier with a 2048² map at **255 fps on ATI Radeon X1600 XL with sampling bounds [8, 50]** (vs 32 fps for the 1.5 M-polygon reference); ToyShop cobblestones and bricks used 8–40 samples per pixel; extruded text / sharp cones "> 15 fps on ATI Radeon X1600 XL rendering at 1600x1200". — same source
- Dynamic height fields: "Our method can be used with a dynamically rendered height field and still produce perspective-correct depth results. In that case, the dynamically updated displacement values can be used to derive the normal vectors at rendering time by convolving the height map with a Sobel operator... The rest of the algorithm does not require any modification." Also demoed with "shadow mapping integrated and dynamic view-dependent reflections". — same source
- SM2 limit: in the SM 2.0 version "we are unable to compute more than 8 samples during ray tracing in a single pass"; multi-pass via off-screen buffers is the workaround. — same source
- Limitations: aliasing when the height field has frequencies above the sampling rate; "lack of detailed silhouettes" — artists hide it with border geometry (curb stones, corner bricks). — same source

**Policarpo & Oliveira, GPU Gems 3 ch. 18 "Relaxed Cone Stepping for Relief Mapping"**
- Relief mapping = linear search to bracket, then binary search to refine, in 2D texture space with the ray scaled so z = 1; relaxed cone stepping uses a precomputed per-texel cone ratio (offline O(n²), 128 search steps) and at runtime a fixed **15 cone steps + 6 binary-search steps**; cone ratio can share the depth texture's channel; cone maps must not be ordinarily mip-mapped; per-iteration logic raises register pressure and lowers occupancy; relief texture in the example is 256×256; z-buffer updates and self-shadowing are covered; dynamic height maps are not discussed (the cone map is a precomputation, so it does not apply to a per-frame height field). — [GPU Gems 3 ch. 18](https://developer.nvidia.com/gpugems/gpugems3/part-iii-rendering/chapter-18-relaxed-cone-stepping-relief-mapping)

**Other step-count conventions [S]**
- PlayCanvas's POM treats the tap count as a cap (default 16 in occlusion mode), uses fewer taps head-on and for shallow relief, and spends nothing once the ray covers less than a texel; Unreal's docs call POM "very expensive" and advise against using it everywhere. — [search snippet summarising PlayCanvas / Unreal docs](https://developer.playcanvas.com/user-manual/graphics/physical-rendering/parallax-mapping/) [S]
- Unigine's POM node exposes a max layer count for steep angles and a min layer count for head-on views. — [Unigine docs](https://developer.unigine.com/docs/latest/content/materials/graph/node_library/misc/parallax_occlusion_mapping) [S]

### Inferences
- [I] For Hydrophobia's grid the simulation already supplies what Valve had to author: a per-cell velocity field at 1 texel per 20 units (Valve used ~4 texels/m, i.e. much denser, but a bilinearly filtered coarse flow map is fine for ripple advection because the ripple normal map itself is tiled far more finely). The Valve recipe therefore costs ~2 fetches + ~21 ALU on top of the existing water shader and runs on ps2.0b, so it is the baseline to beat before any ray marching is considered.
- [I] Chentanez & Müller's variant is the same two/three-phase advection but with texcoords advected *on the simulation grid* (CPU or CUDA) and interpolated by the vertex shader; on a D3D9 target the texcoord advection can be done on the CPU per cell (3 float2 per cell, semi-Lagrangian) and uploaded as vertex attributes — no compute needed. Their stretch-fade weight ξ = e^(−βμ) is what prevents the "unnaturally distorted small waves" artifact; a cheaper proxy is Valve's "scale normal strength by flow speed".
- [I] POM over a flow-advected ripple field: the marched height must be the blended height `wA·hA(uvA) + wB·hB(uvB)` (or the DH-map height channel), so each march step costs 2 fetches rather than 1; with Tatarchuk's bounds [8, 32] that is 16–64 fetches/pixel before shading. Alternatively march a single *simulation-independent* ripple height texture and only use the flow-advected layers for the normal; the parallax then disagrees slightly with the normal but is visually acceptable for low height scales.
- [I] The ripple height scale on water is tiny relative to the ripple wavelength (a few units at most on 20-unit cells), so the parallax offset vector P is short, few steps are needed, and the in-shader LOD threshold can be aggressive (POM only within a few metres, bump mapping beyond). The silhouette limitation of POM is irrelevant for a water sheet viewed from above (no silhouettes against the sky), which removes POM's worst artifact for this use.

### Gaps
- No published source found that applies POM/relief ray marching specifically to an *animated water ripple* height field; Tatarchuk's dynamic-height-field support is stated generically (she used it for other displacement effects).
- McGuire & McGuire 2005 "Steep Parallax Mapping" (the origin of view-angle-adaptive layer counts) could not be fetched (PDF URL 404); its layer counts are not cited here.
- The UDK (UE3, D3D9/SM3) "Parallax Occluded Mapping" developer gem page, which would have given UE3-era instruction counts, returns 403 / redirects and could not be read.
- No GTX 400 / Radeon HD 5000 benchmark of POM was found; the only hard numbers are Tatarchuk's X1600 XL (2006) and Chentanez's GTX 480 (whose rendering cost is folded into the total frame time, 8–13 ms including CUDA simulation).

## Key question 2 — Interior mapping (van Dongen 2008) and "parallax cube"/fake-interior descendants: can the ray-vs-box idea render a shallow water volume (floor, suspended particles, detritus layers)? Published liquid/ice/layered-material examples?

### Takeaway
Interior mapping is a per-pixel ray cast against a regular lattice of axis-aligned planes in object space (ceil/floor via `ceil(y/d)·d`, walls likewise, nearest of three), cheap enough for ps 2.0's 64-instruction limit and costing ~5× a diffuse+reflection material on a GeForce 6600 GT; van Dongen's "furniture plane" (an alpha-tested plane parallel to the surface at a fixed inset depth) is exactly the primitive needed for a suspended-detritus layer. No published example of interior mapping applied to water, puddles or aquaria was found; the closest published relatives are single-offset "parallax ice" (floor texture offset along the view ray by a depth parameter) and layered-ice materials (POM-offset albedo plus height-based internal emission). A "water interior" is therefore an [I] inference built from verified primitives, not a documented technique.

### Cited Findings

**van Dongen, "Interior Mapping: A new technique for rendering realistic buildings", Computer Graphics International 2008**
- Core: "raycasting in the pixel shader is used to calculate the positions of floors and walls behind the windows"; buildings stay simple cubes; "The number of rooms rendered does not influence the framerate or memory usage"; rooms "can have furniture and animated characters". — [van Dongen 2008 PDF](https://www.proun-game.com/Oogst3D/CODING/InteriorMapping/InteriorMapping.pdf)
- Ceilings: space has ceilings at regular distance d (planes parallel to XZ); pixel position and camera are transformed to object space; the ceiling above the pixel is at `ceil(y/d)·d` (camera tilted up) or `(ceil(y/d) − 1)·d` (tilted down, i.e. the floor); intersect the camera→pixel ray with that plane; use the intersection's x,z (scaled by a constant) as the texture UV. Walls use the same calculation with XY and YZ planes; "Of the resulting three intersections, the one closest to the camera will be used" and the texture of that plane. Computing in object space lets buildings rotate. An exactly horizontal ray divides by zero but "GPUs do not crash on this and the visual artefacts... are so rare... negligible". — same source
- Instruction budget: "the number of shader instructions is small enough to be able to calculate the effect within the 64 instructions allowed in pixel shader model 2.0, and also add a diffuse and reflection map in the same pass". — same source
- Windows: the diffuse texture's alpha stores where windows are (1 = exterior, 0 = interior colour); interior colour is blended with a reflection map. — same source
- Furniture plane: "an extra plane that is parallel to the surface of the building, but displaced a fixed distance to the inside... defined in the pixel shader. It is intersected with the ray... if the intersection is closer than the interior planes, then the furniture is shown"; its texture alpha "determines whether the colour of the furniture plane is discarded or not"; animated textures can be used. Caveat: "unlike the interior planes, the furniture plane is not geometrically correct. If the building's surface is curved or has a corner... the stronger the distortion" — avoid on highly curved objects. — same source
- Performance (1024×768, Athlon 2500+, **GeForce 6600 GT 128 MB**, frames per 5 s): diffuse + window reflections material 5,100 frames; same material with Interior Mapping 999 frames (≈5.1× cost); four 256² interior textures 999 → 64² 1032 → 16² 1053 (texture resolution "only resulted in a 5% performance increase"); rooms per building 1,000 → 4,000,000: no change; enabling z-cull 881 → 1265 frames (+44%); four separate textures perform the same as one textured ceiling with lit walls; reading all walls from a single atlas texture was *slower* due to the extra selection instructions. Interior Mapping overtakes polygonal interiors at 100 buildings (5,000 vs 79,000 polygons). Results reproduced on 13 other machines with similar ratios. — same source
- Extensions: lit/unlit rooms by 3D noise with probability c; random room texture from a texture atlas; varying room sizes with bounded wall displacement (only two candidate walls need checking, keeping constant time). Complexity "linear in the number of pixels on the screen, but constant in the number of buildings, windows, ceilings, floors and walls" — automatic LOD with distance. — same source

### Inferences
- [I] A "water interior" is a degenerate interior map: an **open box** with only a floor plane (at depth = simulated water depth h, which the shallow-water sim provides per cell) and 1–3 "furniture planes" at fixed insets (e.g. 0.2h, 0.5h) carrying alpha-tested detritus/particle sprites. Walls are only needed where water meets vertical geometry (tank/corridor walls) — and even there the real geometry is usually rendered behind, so skip them. The per-pixel work is one ray-plane intersection per layer (`t = −d_layer / V_ts.z`, `uv = uv0 + V_ts.xy * t`), i.e. a handful of instructions per layer plus one fetch — far below van Dongen's 64-instruction ps2.0 budget.
- [I] van Dongen's furniture-plane caveat ("not geometrically correct" on curved or cornered surfaces) applies mildly here: the water surface is a height field, not a plane, so a plane defined "parallel to the surface" tilts with the local slope. Using the mean water plane (or the simulation's cell plane) as the reference, and the tangent-space view vector from the *geometric* normal (not the ripple normal), keeps layers consistent across the sheet; adding the ripple normal's xy to the per-layer offset (as the Godot ice shader does) gives cheap refraction wobble.
- [I] Layer ordering/compositing: intersect layers front-to-back, each layer is `lerp(result, layerColor, layerAlpha * T(t))` where `T(t) = exp(−σ·t)` with t the in-water ray length to that layer — this reproduces the PaintBlob "fog scaled by thickness" look and Catlike's depth fog with per-layer depths that vary correctly with view angle (grazing views see more fog before reaching the floor).
- [I] Because the floor in a shallow-water game is usually real geometry already in the refraction buffer, the interior-mapped floor is only worthwhile when (a) the water is drawn opaque (no refraction pass), (b) a decorative sub-surface layer (silt, caustic sheet, weed) is wanted at a depth that is *not* the real floor, or (c) the renderer cannot afford a grab/refraction copy per frame. Suspended detritus (b) is the genuinely new capability — Portal 2's debris was a 2D flowed colour map on the surface with no depth.
- [I] Cost ordering on 2011 hardware (from van Dongen's 6600 GT ratios): a 1-floor + 2-detritus-plane water interior is roughly comparable to van Dongen's full 3-plane interior (≈5× a textured+reflective surface at 1024×768 on a 2005 GPU); on GTX 400 / HD 5000 class hardware this is a few percent of a frame for a screen-filling water sheet. No direct measurement exists (see Gaps).

### Gaps
- No published example of interior mapping / parallax cubes used for water, puddles, aquaria, or any liquid was found after targeted searches; the technique's application to water is an inference.
- Insomniac has not published its Spider-Man window technique; everything about it is third-party analysis.
- The UDK Interior Mapping gem (a D3D9/SM3 implementation) could not be fetched.
- The Tiny Tina's Wonderlands ice and the Vikings: Valhalla pages were only available as snippets; no numbers (depth values, instruction counts) are available.

## Key question 3 — Steep/depth parallax for puddles and shallow water: floor texture parallax-offset by water depth to fake refraction depth ("parallax refraction")

### Takeaway
Production "fake refraction" on D3D9-era hardware is screen-space UV perturbation of a scene copy (Sousa, GPU Gems 2, Far Cry/CryEngine: normal.xy × 0.05–0.075, with an alpha mask to stop foreground leakage) plus depth-buffer-based fog (Catlike: `exp2(−density·depth)`, density ≈ 0.1–0.15, refraction offset scaled by `saturate(depthDifference)`); parallax-offsetting a *floor texture* by water depth is documented only in small shaders and tech-art posts (Godot parallax ice, Lens Studio Parallax Coords, opaque-water ArtStation pieces) as a single-step offset along the view ray — no steep/occlusion variant for water was found in a primary source.

### Cited Findings
- Sousa, GPU Gems 2 ch. 19 "Generic Refraction Simulation" (Crytek, 2005): render opaque scene to texture S (the back buffer), draw the refractive surface sampling S at projected screen UV + normal-map XY × scale; **refraction mask**: clear S's alpha to white, render refractive meshes to alpha only (black), and if the perturbed sample lands on a masked texel fall back to the unperturbed sample. Scales: basic 0.05; water refraction 0.075 (4 averaged bump layers), water reflection 0.02 with Fresnel bias 0.2 / power 5; glass 0.2 with bias 0.4; deep-water fade "10 / distance"; single pass; "could be adapted to pixel shader 1.1–1.4 hardware"; overlapping refractive surfaces of different colours are wrong without sorting. Expands Far Cry's water/heat-haze/scope techniques. — [GPU Gems 2 ch. 19](https://developer.nvidia.com/gpugems/GPUGems2/gpugems2_chapter19.html); citation via [O'Reilly](https://www.oreilly.com/library/view/gpu-gems-2/9780321545411/ch19.html)
- Catlike Coding "Looking Through Water": `uvOffset = normal.xy * _RefractionStrength` (default 0.25, "rather strong" at 1), aspect-corrected, added to screen position before perspective divide; sample snapped to texel centres to remove thin artifact lines; `depthDifference = LinearEyeDepth(depthTex) − surfaceDepth`; fog `lerp(fogColor, background, exp2(−density * depthDifference))`, density 0.15 used; if `depthDifference < 0` (sample hit something in front of the water) resample at the unperturbed UV, or scale the offset by `saturate(depthDifference)`; requires a depth texture (MSAA off in that path) and a grab pass shared by all water surfaces; doesn't work with vertex-displaced waves that lack tangent-space normals. — [Catlike Coding](https://catlikecoding.com/unity/tutorials/flow/looking-through-water/)
- OpenMW refraction-fog fix: depth must be re-sampled *after* the screen-UV offset is applied, otherwise fog misaligns at sharp depth changes. — [OpenMW MR !2922](https://gitlab.com/OpenMW/openmw/-/merge_requests/2922) [S]
- Godot Parallax Ice (single-step floor parallax, full code above): floor UV offset = `normalize(p − ro − n·refractive_index).xz · depth` (+ `n.xy`), `depth` default 0.1. — [godotshaders.com](https://godotshaders.com/shader/parallax-ice-for-fake-depth-to-plane-meshes/)
- Opaque-water floor parallax in shipped/portfolio art (Vikings: Valhalla; stylised water with distance-field depth). — [ArtStation](https://godsgreg.artstation.com/projects/YBnXEV) [S]; [ArtStation](https://guilmeer-gcb.artstation.com/projects/LRy8rK) [S]
- Basic parallax mapping (Kaneko et al. 2001, "Detailed Shape Representation with Parallax Mapping", ICAT 2001) displaces texture coordinates by view angle in tangent space scaled by the height value — "a single step process that does not account for" occlusion; steep-parallax methods (POM, relief, interval, cone-step, relaxed cone) trace rays against the height field. — [Wikipedia: Parallax mapping](https://en.wikipedia.org/wiki/Parallax_mapping)

### Inferences
- [I] "Parallax refraction" for a floor texture is the Kaneko single-step offset with the height replaced by the water depth h and the direction replaced by the *refracted* tangent-space ray: `V_r = refract(−V_ts, (0,0,1), 1/1.33)`, `uv_floor = uv − V_r.xy / V_r.z · h / floorTextureScale`. Because h is smooth (one value per 20-unit cell, bilinear) there is no occlusion to resolve, so a single step is exact for a flat floor — the only error is the floor's own relief, which is why no steep/occlusion variant is needed and why none is published.
- [I] Where the floor is real geometry, the depth-fog + screen-space perturbation route (Sousa/Catlike) is both cheaper and more correct; the floor-parallax route wins only for an opaque water pass, for a decorative sub-floor layer, or when the real floor is far below and a faked near floor (silt layer) is wanted.
- [I] The depth-buffer rejection (`depthDifference < 0`) and the Sousa alpha mask are both needed on D3D9: without them, ripples with large normal.xy pull above-water geometry into the refraction. Hydrophobia-style flooded corridors have lots of geometry just above the waterline, so this matters more than for open water.

### Gaps
- No Naughty Dog / Insomniac / Crytek talk describing a depth-parallax puddle or "parallax refraction" shader was found; CryEngine docs surfaced only a "Silhouette POM" page (not read).
- Snippets of the OpenMW and ArtStation sources were not verified against the full pages.

## Key question 4 — Limits: silhouettes, grazing angles, aliasing at distance, interaction with planar reflection/refraction passes, dynamic vs static height maps, cost of per-pixel ray marching on 2011 hardware and what SM3 implies

### Takeaway
SM3 (ps_3_0) guarantees ≥512 instruction slots, dynamic flow control nested to 24, 32 temporaries, 16 samplers, gradient instructions and no dependent-read limit, so Tatarchuk-style adaptive loops with `tex2Dgrad` fit comfortably; the practical constraints are (1) branch coherence — GeForce 6-era SIMD groups execute one path, divergent groups pay both sides, so view-angle-adaptive loop counts are efficient only because they vary smoothly across the screen — (2) aliasing: sample at >2× the height map's spatial frequency or fall back to bump mapping via explicit mip LOD, (3) relief/cone methods that need precomputed cone maps are out for a per-frame simulated height field, and (4) parallax changes texture lookups only, so reflection/refraction passes must be perturbed by the resulting *normal* and masked against the depth buffer; silhouettes are a non-issue on a top-down water sheet.

### Cited Findings
- ps_3_0 caps (Microsoft): dynamic flow control (`if bool`, `break`, `break_comp`) nesting 0–24; 32 temporary registers; `loop`/`rep` nesting 4; gradient instructions `dsx`, `dsy`, `texldd`; predication; no dependent-read limit; no texture-instruction limit; "Each pixel shader is allowed anywhere from 512 up to... MaxPixelShader30InstructionSlots (not more than 32768). The number of instructions run can be much higher because of the looping support. MaxPShaderInstructionsExecuted should be at least 2^16"; 16 samplers; 4K textures; anisotropy 16. — [Microsoft ps_3_0 reference](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx9-graphics-reference-asm-ps-3-0)
- SM2 vs SM3 for POM: SM 2.0 "suffers from a small instruction count limit, and thus we are unable to compute more than 8 samples during ray tracing in a single pass"; the SM3 version uses dynamic flow control for the adaptive count and early-out; the mip level is computed explicitly "on SM 3.0 hardware" for the LOD system. — [Tatarchuk 2006](https://advances.realtimerendering.com/s2006/Chapter5-Parallax_Occlusion_Mapping_for_detailed_surface_rendering.pdf)
- Branching cost (GPU Gems 2 ch. 34, GeForce 6 era): fragments run in SIMD groups and "each group can execute only one branch"; divergent groups fall back to predication so both sides run; incoherent branching costs roughly both paths plus overhead; branches are efficient when spatially coherent; predication is preferred for short branches of ~2–4 operations; group size is not stated. — [GPU Gems 2 ch. 34](https://developer.nvidia.com/gpugems/gpugems2/part-iv-general-purpose-computation-gpus-primer/chapter-34-gpu-flow-control-idioms)
- Valve's water shader had to fit ps2.0b and Xbox 360 and was "already at perf limits on the Xbox 360 & low-end PC" — the flow technique was chosen partly because it is branch-free and adds only 21 ALU + 2 fetches. — [Vlachos 2010](https://www.advances.realtimerendering.com/s2010/Vlachos-Waterflow(SIGGRAPH%202010%20Advanced%20RealTime%20Rendering%20Course).pdf)
- Aliasing/grazing: relief mapping shows "sampling aliasing at grazing angles" and stair-stepping from 8-bit intersection precision; depth bias flattens features; POM's piecewise-linear intersection removes the stair-stepping but still aliases if the height field has features above the sampling rate; at grazing angles the step is "frequently much larger than a texel". LOD: full POM only below mip threshold (4), bump mapping above, blended by fractional mip. — [Tatarchuk 2006](https://advances.realtimerendering.com/s2006/Chapter5-Parallax_Occlusion_Mapping_for_detailed_surface_rendering.pdf)
- Relaxed cone stepping needs an offline O(n²) cone-map precomputation and cone maps must not be mip-mapped conventionally; too few cone steps give distortion; extra loop logic raises register use and lowers occupancy. — [GPU Gems 3 ch. 18](https://developer.nvidia.com/gpugems/gpugems3/part-iii-rendering/chapter-18-relaxed-cone-stepping-relief-mapping)
- Silhouettes: POM has a "lack of detailed silhouettes", hidden by border geometry; curved silhouettes for relief mapping require Oliveira & Policarpo 2005's per-vertex quadric fit. — [Tatarchuk 2006](https://advances.realtimerendering.com/s2006/Chapter5-Parallax_Occlusion_Mapping_for_detailed_surface_rendering.pdf); [GPU Gems 3 ch. 18](https://developer.nvidia.com/gpugems/gpugems3/part-iii-rendering/chapter-18-relaxed-cone-stepping-relief-mapping)
- Interaction with reflection/refraction: Tatarchuk integrated "shadow mapping... and dynamic view-dependent reflections" with POM (Figure 1a); Sousa's refraction mask and Catlike's depth-difference check are the standard guards against foreground leakage when screen UVs are perturbed; Valve's requirement was to "Work with existing reflective surfaces". — sources as above
- Interior mapping distance behaviour: complexity "linear in the number of pixels... constant in the number of... rooms"; texture resolution barely affects cost (5% from 256² to 16²); z-cull gave +44%, so drawing the water after opaque geometry (early-z) matters. — [van Dongen 2008](https://www.proun-game.com/Oogst3D/CODING/InteriorMapping/InteriorMapping.pdf)
- Reference 2011-class GPU cost of the *simulation side*: Chentanez & Müller's full pipeline (CUDA height-field sim with FFT texcoord advection + particles + rendering) runs 8–13 ms per frame on a GTX 480 at 128²–256² grids. — [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf)

### Inferences
- [I] On a 2011 GTX 400 / HD 5000 (DX11 parts running a D3D9 path), Tatarchuk's 2006 numbers (8–50 samples, 255 fps on a mid-range X1600 XL at a character's screen footprint) scale to a full-screen water sheet comfortably; the realistic budget risk is not ALU but texture bandwidth at 2 fetches/step on a flow-blended height plus the refraction/reflection samples. Keep POM min/max steps at ~[6, 24] for a low-amplitude ripple field and let the explicit-mip LOD cut to bump mapping beyond a few cells' distance.
- [I] Dynamic branching cost: adaptive step counts and early-out are coherent over a water sheet (view angle varies smoothly), which is exactly the "spatially coherent branch" case GPU Gems 2 says is efficient; the only incoherent branch is the per-layer alpha test of detritus sprites, which should be done with `lerp` (predication), not `if`.
- [I] Dynamic vs static: everything that precomputes per-texel data (cone maps, distance maps, Donnelly's distance functions, view-dependent displacement maps) is unusable for a per-frame height field; only linear-search POM / steep parallax (and the single-step offsets) remain. For the *tiled ripple texture* (static, flow-advected) a cone map could be precomputed — but the two-phase blend means the marched height is a time-varying mix of two texture lookups, which again invalidates the cone bound. So: plain linear search.
- [I] Parallax does not move the depth-buffer surface. Objects intersecting the water (legs, debris) will cut the surface at the geometric height, not the ripple height; at ≤ a few units of ripple amplitude this is invisible, which is another reason to keep ripple parallax amplitude small (and why Valve/Chentanez use bump-only ripples for the normal and reserve displacement for the coarse height field).
- [I] For planar reflection: perturb the reflection UV by the POM-derived normal (Sousa used a smaller scale for reflection, 0.02, than refraction, 0.075); do not add the texture-space parallax offset to screen-space UVs — they live in different spaces.

### Gaps
- No vendor data on branch granularity for the specific 2011 parts (GF100 / Evergreen) was found; the GPU Gems 2 article gives no pixel counts.
- No measured POM frame cost on GTX 400 / HD 5000 hardware was found.
- Whether Hydrophobia's PC renderer exposes a refraction copy or depth texture to the water shader was not determined; no technical write-up of HydroEngine's rendering (as opposed to simulation) was found — only press pieces stating the water "flows" and that ripples come from a reactive real-time surface. — [MCV](https://mcvuk.com/development-news/blade-sharpens-hydroengine) [S]; [TheSixthAxis preview](https://www.thesixthaxis.com/2010/09/24/preview-hydrophobia/comment-page-2/) [S]

## Key question 5 — Concrete recipes: pseudo-shader outlines and parameter ranges (steps, depth scale, texture sizes)

### Takeaway
Three stackable recipes, ordered by cost: (A) flow-advected ripple normals driven by the simulation velocity (ps2.0b-class, +2 fetches +21 ALU), (B) a single-step "water interior" — floor + 1–3 alpha-tested detritus planes intersected along the refracted tangent-space view ray with per-layer transmittance (ps2.0-class, a few fetches), and (C) POM over the ripple height for close-ups only (SM3, 6–24 adaptive steps, explicit-mip LOD to bump mapping). Parameters below are from the cited sources where given and marked [I] where chosen by me.

### Cited Findings (parameter values from sources, gathered)
- Flow map ~4 texels/metre; two layers half a phase apart; noise texture de-syncs phases; normal strength scaled by |flow|; cost +2 fetches, +21 ALU. — [Vlachos 2010](https://www.advances.realtimerendering.com/s2010/Vlachos-Waterflow(SIGGRAPH%202010%20Advanced%20RealTime%20Rendering%20Course).pdf)
- Two-phase formulas, jump 0.2–0.25 per phase, FlowOffset −0.5..0, DH-map derivative summation, `heightScale = speed·Modulated + Constant`. — [Catlike Coding](https://catlikecoding.com/unity/tutorials/flow/texture-distortion/)
- Three advected texcoord sets per cell, τ ≈ 3 s, phase shift τ/3, weights `(1/3)(1−cos(2π(t−t0)/τ))`, stretch fade `e^(−βμ)` with β 0.5–2; FFT texture bump-mapped everywhere, displacement only on a ¼Δx render grid. — [Chentanez & Müller 2010](https://matthias-research.github.io/pages/publications/hfFluid.pdf)
- POM: `n = lerp(nMax, nMin, N·V)`, bounds [8,50] (character) / 8–40 (cobblestones), piecewise-linear intersection, `tex2Dgrad` in loop, LOD mip threshold 4 → bump mapping, height in normal-map alpha, textures 128²–2048². — [Tatarchuk 2006](https://advances.realtimerendering.com/s2006/Chapter5-Parallax_Occlusion_Mapping_for_detailed_surface_rendering.pdf)
- Relief/RCS: 15 cone steps + 6 binary; 256² relief texture. — [GPU Gems 3 ch. 18](https://developer.nvidia.com/gpugems/gpugems3/part-iii-rendering/chapter-18-relaxed-cone-stepping-relief-mapping)
- Screen-space refraction scale 0.075 (water), reflection 0.02, Fresnel bias 0.2 pow 5, alpha-mask fallback. — [GPU Gems 2 ch. 19](https://developer.nvidia.com/gpugems/GPUGems2/gpugems2_chapter19.html)
- Refraction strength 0.25 (Unity, normal.xy units), fog `exp2(−0.15·depth)`, offset × `saturate(depthDifference)`. — [Catlike Coding](https://catlikecoding.com/unity/tutorials/flow/looking-through-water/)
- Interior mapping: `ceil(y/d)·d` plane selection, nearest of three planes, furniture plane at fixed inset with alpha test, ps2.0 64-instruction budget, ~5× cost of diffuse+reflection on 6600 GT, texture resolution nearly free. — [van Dongen 2008](https://www.proun-game.com/Oogst3D/CODING/InteriorMapping/InteriorMapping.pdf)
- Single-step floor parallax: `offset = normalize(p − ro − n·k).xz · depth`, depth 0.1, k 0.1. — [godotshaders.com](https://godotshaders.com/shader/parallax-ice-for-fake-depth-to-plane-meshes/)

### Inferences — the recipes [I]

**Shared inputs from the simulation (per vertex / per cell, bilinear in the pixel shader):** water height η, velocity u (2D), depth above floor h = η − floor, and optionally foam/age. Upload as a vertex stream on the 20-unit grid or as small textures (grid-sized, e.g. 128²–256² R16G16 for u, R16 for h) — D3D9 can read textures in vs_3_0 (vertex texture fetch) but it is simpler and more portable to pack them into vertex attributes.

**Recipe A — simulation-driven flow ripples (Valve/Chentanez hybrid, ps2.0b-safe)**
```
// VS: pass uv (world-scaled, e.g. 1 tile per 20..40 units), tangent-space V, flow = u * FlowStrength, noise
// PS:
float2 f   = flow;                           // 2D velocity in uv units/sec
float  t   = time * Speed + noise;           // noise: low-freq Perlin, A channel of flow/noise texture
float  pA  = frac(t),       pB = frac(t + 0.5);
float  wA  = 1 - abs(1 - 2*pA), wB = 1 - abs(1 - 2*pB);
float2 uvA = (uv - f*(pA + FlowOffset))*Tiling + 0.0 + (t - pA)*jumpA;
float2 uvB = (uv - f*(pB + FlowOffset))*Tiling + 0.5 + (t - pB)*jumpB;
float4 dhA = tex2D(RippleDH, uvA), dhB = tex2D(RippleDH, uvB);   // DH map: A,G = d h/dx, dh/dy ; B = h
float  speed = length(f);
float  hs  = speed * HeightScaleModulated + HeightScaleConstant;  // Valve: bump strength ∝ flow speed
float2 d   = (dhA.ag*2-1)*wA*hs + (dhB.ag*2-1)*wB*hs;
float  hRip= dhA.b*wA + dhB.b*wB;                                  // blended ripple height (for recipes B/C)
float3 nTS = normalize(float3(-d, 1));
```
Parameters: jumpA = (6/25, 5/24)-style, jumpB different; FlowOffset −0.5 for an at-rest-looking peak (Valve's debris rule) or 0 for normals; Tiling such that one ripple tile ≈ 1–2 cells (20–40 units); DH texture 512²–1024² DXT5 (A=dh/dx, G=dh/dy, B=h) — Tatarchuk stores height in alpha for `tex2Dgrad` convenience; a DH map in DXT5 keeps the two high-precision derivative channels in A and G. Optional stretch fade: CPU-advect 3 texcoord sets per cell (Chentanez) instead of the pixel-shader distortion; β ≈ 1, τ ≈ 3 s.

**Recipe B — "water interior" layers (floor + detritus planes), single-step, ps2.0-class**
```
// tangent frame = mean water plane of the cell (geometric normal), V_ts = tangent-space view dir (z up, toward eye)
float3 Vr   = refract(-V_ts, float3(0,0,1), 1.0/1.33);   // refracted ray going down; Vr.z < 0
float2 slope= Vr.xy / max(-Vr.z, 0.05);                  // clamp near-grazing to limit swim (cf. offset limiting)
float2 wob  = nTS.xy * RippleRefract;                    // ripple-driven wobble, ~0.02..0.05 (Sousa 0.075, Catlike 0.25 are screen-space analogues)
// Floor at simulated depth h (per-pixel), texture in world units:
float2 uvFloor = uvWorld + (slope * h + wob) * FloorTexScale;
float3 floorC  = tex2D(FloorTex, uvFloor).rgb;
float  tFloor  = h / max(-Vr.z, 0.05);                   // in-water path length
float3 col     = lerp(WaterFogColor, floorC, exp2(-Sigma * tFloor));   // Catlike fog form, Sigma≈0.1..0.2 per unit → scale to 20-unit cells
// Detritus / suspended layers at fixed insets d_k (e.g. 0.25h, 0.6h), nearest first:
for k in [near..far]:                                    // unrolled, 1..3 layers
    float2 uvK  = uvWorld + (slope * d_k + wob*0.5) * LayerTexScale_k + flowScroll_k;   // flowScroll = advected like Recipe A or just u*time
    float4 sprK = tex2D(DetritusTex_k, uvK);             // alpha-tested sprite sheet (van Dongen "furniture plane")
    float  tK   = d_k / max(-Vr.z, 0.05);
    col = lerp(col, sprK.rgb, sprK.a * exp2(-Sigma * tK));   // composite front-to-back by alpha × transmittance
```
Then apply Fresnel-blended reflection and the surface specular from nTS. Notes: use the *geometric* (cell) normal for the tangent frame so all layers share one box; use the ripple normal only for `wob`. Where the real floor is in the refraction buffer, replace `floorC` by the Sousa/Catlike screen-space sample (offset by nTS.xy × 0.075, masked by alpha / depthDifference) and keep only the detritus planes from this recipe — that gives true floor + fake suspended layers for ≈ 2–3 extra fetches. Clamp of `-Vr.z` is the only guard against the grazing-angle division blow-up that van Dongen notes.

**Recipe C — POM over the ripple height for close-ups (SM3 only)**
```
// Only when explicit mip level (Tatarchuk) <= LODThreshold, else use nTS from Recipe A directly.
int   n     = (int) lerp(nMax, nMin, dot(N_geo, V));     // nMin 6..8, nMax 16..24 for low-amplitude ripples [I]; Tatarchuk used [8,50]
float2 P    = -V_ts.xy / V_ts.z * RippleHeightScale;     // parallax offset vector; RippleHeightScale in uv units (small: ripple amplitude / tile size)
float2 step = P / n;  float dh = 1.0/n;
float  bound = 1.0, prevH = 1.0; float2 uvC = uv;  bool hit=false;
[loop] while (!hit && i < n) {                            // uses dynamic flow control; tex2Dgrad with dx,dy from outside the loop
    uvC -= step; bound -= dh;
    float hC = blendedRippleHeight(uvC);                  // = wA*tex2Dgrad(DH,uvA(uvC)).b + wB*tex2Dgrad(DH,uvB(uvC)).b  (2 fetches)
    if (hC > bound) { /* piecewise-linear segment intersection between (prevH,bound+dh) and (hC,bound) */ hit=true; }
    prevH = hC; i++;
}
uvPOM = uv - offsetFromIntersection;                     // then sample dhA/dhB at uvPOM for the normal, and use uvPOM as uvWorld in Recipe B
```
Texture 512²–1024² ripple DH/height; sample ≥ 2× the ripple's highest spatial frequency; LOD threshold mip ≈ 3–4 so POM runs only within a few metres; expect ~2×n fetches per pixel. Because ripple amplitude is small, P is short and n can sit near nMin most of the time; the silhouette limitation does not apply to a top-down sheet.

**Budget sketch on D3D9 SM3 (per pixel, fetches):** A = 2 (DH) + 1 (flow/noise, if not in vertex stream) ; B = 1 floor (or 1 refraction + 1 depth) + 1–3 detritus + 1 reflection ; C adds 2×n (12–48). Everything above stays well under ps_3_0's 512-slot minimum; A+B fit ps_2_0's 64 arithmetic slots in the spirit of van Dongen's and Valve's budgets (unverified for the exact code above).

### Gaps

- No source gives a validated "offset limiting" rule for single-step water-floor parallax at grazing angles; the `max(−Vr.z, 0.05)` clamp is a guess in the spirit of Welsh's offset-limited parallax (not fetched/verified).
- Whether Hydrophobia's PC water pass renders after opaque geometry with a usable scene copy / depth texture (needed for the refraction variant of Recipe B) is unknown.
